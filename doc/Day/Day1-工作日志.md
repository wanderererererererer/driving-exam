## 三、完成的工作

**数据库设计：**

- 确定系统共 **15 张表**，并完成建表 SQL：

  | 分类 | 表 |
  |---|---|
  | 用户与权限 | `sys_user` |
  | 题库与知识体系 | `knowledge_point`、`question`、`question_option` |
  | 试卷与考试 | `exam_paper`、`exam_paper_question`、`mock_exam` |
  | 学习行为与学情 | `answer_record`、`wrong_book`、`student_subject_status` |
  | 关系与预约 | `coach_student`、`appointment` |
  | AI 问答 | `ai_chat_record` |
  | 教练-学员聊天 | `chat_session`、`chat_message` |

- 核心设计约束：
  - `subject_code` 作为科目维度字段，贯穿 **9 张表**（knowledge_point、question、exam_paper、answer_record、wrong_book、mock_exam、appointment、ai_chat_record、student_subject_status）。
  - **科目一 / 科目四共用刷题逻辑**，通过 `subject_code` 区分；**科目二 / 科目三共用预约逻辑**，通过 `subject_code` 区分。
  - **不建物理外键**，统一使用"逻辑外键 + 索引"。
  - 主数据表带 `deleted` 逻辑删除（0 未删、1 已删），时间字段 `create_time` / `update_time`。
  - 统一字符集 `utf8mb4` / `utf8mb4_unicode_ci`，引擎 InnoDB，主键 BIGINT 自增。
- 在 **DataGrip** 中执行建表 SQL，并导出 `schema.sql` 作为数据库结构文档留存。

## 四、关键技术决策

| 决策点 | 方案 |
|---|---|
| 角色模型 | STUDENT / COACH / ADMIN 三角色，AI 助手内置 |
| 科目组织 | 四个独立页面，科一/四共用刷题、科二/三共用预约 |
| 科目维度 | 统一 `subject_code` 字段贯穿 9 张表 |
| 外键策略 | 不建物理外键，逻辑外键 + 索引 |
| 删除策略 | 主数据逻辑删除（`deleted`），流水表不删 |
| 数据库 | MySQL 8.0，InnoDB，utf8mb4 |
| 预约准入 | 预约无系统前置条件，由教练审批时判断 |

## 五、遇到的问题及解决方案

**问题 1**

- 现象：原计划按"10~12 张表"设计，实际梳理功能后发现题目、选项、试卷、组卷、模拟考试、进度、会话、消息等无法压缩。
- 原因：刷题、考试、预约、聊天、AI 五条业务线的数据实体差异较大，强行合并会破坏表职责单一性。
- 解决：确定为 **15 张表**，并在设计说明中记录"表数量上浮是业务线拆分的结果，而非设计冗余"。

**问题 2**

- 现象：科一与科四、科二与科三功能高度相似，若各自建表会造成大量重复。
- 原因：两类科目只是题库/业务规则不同，结构完全一致。
- 解决：抽取 `subject_code` 统一维度字段，**共用同一套表与业务逻辑**，用科目编码区分；该决策直接决定了后续"科一/科四共用刷题模块、科二/科三共用预约模块"的实现方式。
