## 二、今日目标

补上接口级的**角色鉴权**：让"已登录但角色不对"的请求也被拦下，而不是只拦"没登录"。

## 三、完成的工作

**数据库设计：** 无。

**后端：**

- **新建 `config/PathRoleRule`**（路径 → 角色规则表）：
  - 用 `record Rule(pattern, role)` + `List<Rule>` 承载规则，`AntPathMatcher` 做匹配；
  - 规则按顺序匹配，**先命中者生效**：

    | 路径模式 | 允许角色 |
    |---|---|
    | `/api/auth/**` | 全员（已登录即可） |
    | `/api/common/**` | 全员 |
    | `/api/student/**` | `STUDENT` |
    | `/api/coach/**` | `COACH` |
    | `/api/admin/**` | `ADMIN` |

  - 未命中任何规则的路径 → 仅要求登录，不做角色限制；
  - 加规则只需在 `RULES` 里追加一行。
- **改造 `JwtInterceptor`**：在"token 校验通过"之后增加一步角色判定：
  1. 放行 OPTIONS（跨域预检）；
  2. 解析并校验 Bearer token（失败 → **401**）；
  3. 用 `UrlPathHelper.getPathWithinApplication(request)` 取路径，交给 `PathRoleRule.isAllowed(path, role)`（不匹配 → **403**）；
  4. 通过后才把 `userId` / `username` / `role` 写入 request 属性。
  - 同时把 401 / 403 的响应写法合并成一个私有方法 `writeJson(...)`，避免重复。
- 验证：以学员 token 访问 `/api/coach/students` → **403**。

**前端：** 无。

**文档/设计：**

- 确立**三层防护链路**：`拦截器（是否登录）` → `规则表（角色对不对）` → `Controller（业务）`。
- 确立**403 不泄露存在性**的原则（沿用 Day 6 的 404 思路）：无权访问就是不告诉你有这个东西。

## 四、关键技术决策

| 决策点 | 方案 |
|---|---|
| 鉴权位置 | **拦截器**统一做，不散落到各 Controller |
| 规则形态 | **独立配置类 `PathRoleRule`**（不写死在拦截器里），便于扩展与测试 |
| 匹配方式 | `AntPathMatcher`（Spring 内建，`.**` 语义与 MVC 一致） |
| 未命中路径 | 仅要求登录，不做角色限制（默认放行到业务层） |
| 状态码 | 401 = 未认证；**403 = 已认证但角色不足**；两者都返回真实 HTTP 状态码 |

## 五、遇到的问题及解决方案

**问题 1**

- 现象：学员 token 可以正常访问 `/api/coach/**`、`/api/admin/**` 等**非本端接口**——只要拿到任意一个有效 token，就能横向访问全部接口。
- 原因：`JwtInterceptor` 此前**只校验"是否登录"**，从不检查角色，属于真实的越权漏洞。
- 解决：新增 `PathRoleRule` 规则表 + 拦截器内的角色判定，不匹配返回 403。**规则抽成独立类**而不是写死在拦截器里，后续加模块只需追加一行配置。

**问题 2**

- 现象：重构后，学员 token 访问未实现的 `/api/student/study/**` 返回 **404**，而访问同样不存在的 `/api/coach/**` 返回 **403**——一开始容易误判为"鉴权没生效"。
- 原因：**两者拦在不同的层**。`/api/student/**` 通过了角色门（学员本来就该访问学生端），一路走到 DispatcherServlet 才发现"没有这个处理器" → 404；`/api/coach/**` 被角色门直接挡下 → 403。
- 解决：确认这是**正确行为**，并沉淀出一条**判断鉴权是否生效的方法论**——
  > **403 与 404 的差别，正是鉴权在起作用的证据**：同一个 token，跨端请求被 403 挡下，本端请求能穿过角色门（只是接口还没写，所以 404）。
