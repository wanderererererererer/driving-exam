## 1. 说明

本文档中的字段名、数据类型、长度与精度、NULL 属性、默认值、主键、唯一键与索引，**一律取自数据库实际建表语句（DDL）**，未依据 Java 实体字段类型反推。采用 MySQL 8.0，字符集统一为 `utf8mb4`、排序规则 `utf8mb4_unicode_ci`，存储引擎为 `InnoDB`。表中"默认值"一列对 `update_time` 字段标注为 `CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`，表示插入时取当前时间、更新时自动刷新。

需要特别区分两类约束：**数据库真实约束**（`NOT NULL`、`DEFAULT`、主键、唯一键、索引）写在 DDL 中，本文档如实列出；而**应用层校验**（如预约日期不得早于当天、时段取值限定为四个固定值、状态流转的合法性）仅由后端代码实现，**数据库层面没有对应的 CHECK 约束或枚举类型**，本文档在相应位置以"说明"方式注明，不作数据库约束表述。

本库共有 **16 张业务表**。其中 14 张有对应的 Java 实体类，且实体字段与表字段逐一对应；`chat_session` 与 `chat_message` 两张表**当前没有对应的实体类与接口实现**（教练与学员聊天功能尚未开发），已在下文标注。

## 3. 正文核心表设计

本节选取 10 张核心表逐一说明，选取依据是它们构成系统的主线数据流：用户与角色（`sys_user`）→ 知识点与题目（`knowledge_point`、`question`、`question_option`）→ 作答与错题（`answer_record`、`wrong_book`）→ 考试与学情（`mock_exam`、`student_subject_status`）→ 师生关系与预约（`coach_student`、`appointment`）。组卷定义表与 AI 记录、会话等表因属于支撑性数据，列于附录数据字典，并在相关处简要提及。

### 3.1 sys_user（用户表）

| `password` | varchar(100) | 否 | — | — | 密码（BCrypt） |
| `real_name` | varchar(50) | 是 | — | — | 真实姓名 |
| `phone` | varchar(20) | 是 | — | 索引(idx_phone) | 手机号 |
| `avatar` | varchar(255) | 是 | — | — | 头像URL |

| `status` | tinyint | 否 | '1' | — | 状态：1正常 0禁用 |
| `create_time` | datetime | 否 | CURRENT_TIMESTAMP | — | 创建时间 |

## 4. 其余 6 张表简述

`exam_paper`（试卷表，12 字段，有逻辑删除）定义试卷的科目、标题、类型、总分、及格分、时长与题目数量，其参数是数据驱动的，模拟考试运行时按该表取值，不在代码中写死。`exam_paper_question`（试卷题目关联表，5 字段）通过唯一键 `uk_paper_question(paper_id, question_id)` 固定一份试卷的题目构成，并用 `score`、`sort_order` 记录每题分值与顺序。

`mock_exam_answer`（模拟考试作答草稿表，6 字段）用于考试进行中的答案暂存，唯一键 `uk_exam_question(exam_id, question_id)` 支持同一题答案的覆盖更新，是断点续考功能的数据基础；交卷后该表的记录会被清空。`ai_chat_record`（AI 问答记录表，11 字段）保存用户提问、模型回答、所用模型与 token 用量，其中 `session_id` 用于把多轮问答组织为一次会话，`references_json` 为后检索增强生成阶段预留的引用来源字段。

`chat_session`（学员教练会话表，9 字段）与 `chat_message`（聊天消息表，7 字段）为师生文字沟通预留，会话表以唯一键 `uk_student_coach(student_id, coach_id)` 固定一个师生对只对应一个会话。**这两张表在当前版本中既没有实体类，也没有对应的接口，属于已设计但未实现的部分。**

## 5. 表间关系说明

本数据库**不使用物理外键**（全部建表语句中 `FOREIGN KEY` 数量为 0），表间关联通过在业务字段上建立普通索引并由应用层维护，例如 `question.knowledge_point_id`、`answer_record.question_id`、`appointment.coach_id` 等。这样做的原因是：逻辑删除与物理外键在语义上并不一致（父记录被逻辑删除后外键仍然成立），且课程设计场景下的数据一致性由服务层保证即可。主要关联关系如下：

- `sys_user` 是主表，其 `id` 被 `answer_record.user_id`、`wrong_book.user_id`、`mock_exam.user_id`、`student_subject_status.student_id`、`coach_student.coach_id` 与 `student_id`、`appointment.student_id` 与 `coach_id`、`ai_chat_record.user_id` 等引用；
- `knowledge_point` 通过 `parent_id` 自关联形成树；`question.knowledge_point_id` 指向知识点；
- `question` 与 `question_option` 为一对多；
- `exam_paper` 与 `exam_paper_question` 为一对多，后者再指向 `question`；`mock_exam.paper_id` 指向所用试卷；`mock_exam_answer.exam_id` 指向进行中的考试；
- `coach_student` 与 `chat_session` 均表示"教练—学员"这一对关系，前者为绑定关系，后者为会话关系。

## 6. 逻辑删除与状态位约定

本库对"删除"采取表分级策略：**主数据表使用逻辑删除字段 `deleted`**（`tinyint`，`NOT NULL DEFAULT 0`），共 5 张——`sys_user`、`knowledge_point`、`question`、`exam_paper`、`appointment`；**流水表与关系表不设 `deleted`**，共 11 张，包括 `answer_record`、`wrong_book`、`mock_exam`、`mock_exam_answer`、`chat_session`、`chat_message`、`coach_student`、`student_subject_status`、`question_option`、`exam_paper_question`、`ai_chat_record`。

不设 `deleted` 的表改用状态位表达变化：`coach_student.status` 以 1 表示有效、0 表示解除，解绑不删除行；`wrong_book.mastered` 标记错题是否已攻克；其余通用状态位（`sys_user.status`、`question.status`、`exam_paper.status`）均以 1 表示有效、0 表示停用。

## 7. 待核实与需注意事项

**7.1 `appointment.status` 的列注释已更新，本文档以最新口径为准。** 数据库结构导出文件（dump，导出时间 2026-10-08 17:26）中，该列的注释仍为四值 `PENDING/CONFIRMED/CANCELLED/COMPLETED`；此后仓库中新增了变更脚本 `sql/alter-appointment-status-comment.sql`，将该列注释更新为五值 `PENDING/CONFIRMED/CANCELLED/REJECTED/COMPLETED`（**仅改注释，列类型仍为 `varchar(20)`、`NOT NULL`、默认 `PENDING`，未改结构**）。本文档采用更新后的五值口径，并在此说明该演进过程，以免与旧快照混淆。**该列的最终值集合仍应以后续在数据库上实际执行 `SHOW FULL COLUMNS` 的结果为准（待核实）。**

**7.2 `status` 类字段均为字符串型，取值由应用层约束。** 数据库中 `appointment.status`、`mock_exam.status` 等列的类型是 `varchar`，取值合法性由后端枚举与业务代码保证，数据库不提供枚举或 CHECK 约束，因此不能表述为"数据库约束了取值范围"。

**7.3 `student_subject_status` 中部分字段尚无写入逻辑。** 该表的 `ai_suggest`、`ai_suggest_time`、`coach_confirm_status`、`coach_remark`、`exam_ready_suggest`、`exam_result`、`exam_date` 等字段已建表，但教练端的 AI 建议与确认、正式考试结果登记等功能尚未实现，这些字段当前在业务中未被写入。

**7.4 字符集与排序规则。** 全部表使用 `utf8mb4` 与 `utf8mb4_unicode_ci`。若后续引入中文拼音排序等需求，需另行评估排序规则。
