# 第 2 章 可行性分析

本章从技术、经济、社会效益、安全与法律五个方面，对本课题所提系统的可行性进行分析，并对课程设计的规模与实施条件作说明。分析中所引用的系统实现情况，均以本项目仓库中的实际源码、数据库结构与已完成的接口测试记录为依据。

## 2.1 技术可行性

### 2.1.1 技术选型与实现基础

本系统采用前后端分离架构。后端基于 Spring Boot 3.2.5 与 Java 17 构建，持久层使用 MyBatis-Plus 3.5.7，数据库为 MySQL 8.0；身份认证采用 JWT（jjwt 0.12.5），密码存储使用 BCrypt（spring-security-crypto）；参数校验使用 Hibernate Validator。后端工程按 Maven 多模块组织，划分为 common（统一响应与异常）、pojo（实体、DTO、VO、枚举）、server（配置、控制器、服务、拦截器、业务包）三个模块，基础包名为 `com.driving.exam`。前端基于 Vue 3 与 TypeScript，构建工具为 Vite，UI 组件库为 Element Plus，状态管理使用 Pinia，路由使用 Vue Router，HTTP 请求封装使用 Axios，图表使用 ECharts。

上述技术均为成熟且长期维护的开源项目，社区资料充足，不存在技术路线上的不确定性。

### 2.1.2 已实现部分的验证情况

截至本报告写作时，系统后端已实现 8 个控制器、共 38 个 REST 接口，覆盖用户认证、学习刷题、错题本、学情分析、智能问答、模拟考试与练车预约七个部分；数据库已建成 16 张业务表，其中 14 张有对应的实体类且字段与建表语句逐一对应。接口层已通过基于 Apifox 的接口回归测试：模拟考试模块的回归报告记录为 **21 请求、83 断言、断言失败 0**，练车预约模块的回归报告记录为 **42 请求、118 断言、断言失败 0**。

关于上述数字需要说明统计口径。两份报告的运行界面上还分别显示了 **1 条**与 **2 条**"失败"，这指的是 Apifox 项目级「默认断言：响应状态码 = 200」与鉴权用例不匹配所致：这几条用例（无令牌访问接口、学员令牌访问教练端接口）按设计应当返回**真实的 HTTP 401 与 403**，而工具的默认断言要求状态码为 200，因此被判为失败；用例自身编写的断言（校验 401/403 状态码与响应体中的错误码）**全部通过**。也就是说，"界面失败数"与"业务断言失败数"是两个不同口径的指标——前者包含工具默认断言的结果，后者才是业务逻辑的校验结果。本项目的工作日志中已按同一口径记录该现象（业务断言失败 0，界面另显示若干条工具误报）。此外，判分逻辑配有单元测试，覆盖全角半角、多选顺序、判断题同义表述、空答案等边界情形。

也就是说，本项目并非停留在方案阶段，核心业务链路在后端已经跑通并有测试记录支撑，这构成了技术可行性的直接证据。

### 2.1.3 关键技术难点的可实现性

本系统涉及若干需要专门处理的技术点，现均已实现并记录在案。判分环节需要在答案表述不统一的情况下保证一致性，实现上通过字符归一化（全角转半角、统一大小写、去除空白与多种分隔符）与双向归一化（标准答案同样归一化），判断题则通过同义词表映射；学情分析环节需要由答题行为推导掌握度，实现上采用"难度加权正确率 × 时间衰减 × 行为修正"的乘积模型，并对结果作区间截断；查询环节为避免逐条关联查询带来的性能问题，统一采用"一次 IN 查询 + 内存分组"的方式装配关联字段；事务方面，仅对涉及多表写入的交卷流程使用事务，并放入独立 Bean 以保证 Spring 事务代理生效。上述做法在实现中均已落地。

### 2.1.4 大语言模型集成的可行性

系统通过 HTTP 调用 DeepSeek 的开放接口完成智能问答。该接口兼容 OpenAI 的调用格式，接入方式为标准 REST 请求，后端只需封装请求体、设置超时、解析响应并作异常分级，不引入额外的模型部署与推理环境，因此不需要 GPU 资源。系统对模型的使用限定为"结合指定科目上下文解释知识点与错题"，提示词由固定规则与动态上下文两部分拼接而成，模型输出结果作为记录存入数据库。该链路已实现并完成联调。

需要说明的是，本版本**未实现检索增强生成（RAG）与向量检索**。其原因在于：一是引入向量数据库、文本切分与嵌入模型调用会显著增加系统复杂度与外部依赖，与课程设计的规模不相称；二是当前题库与知识点数据量有限，通过在提示词中直接注入相关上下文已能覆盖主要问答场景。系统仅在问答记录中预留了引用来源字段、在提示词构建处预留了扩展位置，以便后续升级。因此，本系统当前的问答质量取决于提示词设计与模型本身能力，存在生成内容与事实不完全一致的可能，这一点在使用中需要通过提示学员核对题库与法规原文来缓解。

### 2.1.5 未实现部分的技术评估

尚未实现的功能包括模拟考试与练车预约的前端页面、教练端的学员管理与消息功能、管理员端的用户与题库维护功能。从技术上看，这些功能均为基于已有数据表的常规增删改查与表单页面，接口设计已在接口文档中确定，不涉及新的技术难点，其未完成的原因是开发排期而非技术障碍。

综上，本系统所采用的技术路线成熟、核心部分已实现并验证，未实现部分亦无技术风险，技术上是可行的。

## 2.2 经济可行性

本系统的成本可分为三类：开发与运行环境成本、外部服务成本、人力成本。

**开发与运行环境成本**方面，系统所使用的开发与运行工具全部为开源或免费软件，包括 JDK 17、Maven、Spring Boot、MyBatis-Plus、MySQL 8.0 社区版、Node.js、Vue 3、Element Plus、Pinia、ECharts 以及用于绘图与文档生成的 Graphviz、LibreOffice 等。数据库与后端服务均部署在个人计算机的本地环境中，不需要购买服务器、域名或云主机。此项成本为零。

**外部服务成本**方面，系统的唯一付费环节是大语言模型 API。项目配置文件中的模型别名为 `deepseek-chat`；据项目内的对接记录，服务端实际返回的模型为 `deepseek-flash`。DeepSeek 官方文档站的「Models & Pricing」页（访问日期 2026-10-11）显示，`deepseek-flash` 按**每百万 tokens** 计价：输入（缓存命中）非高峰 **0.003 美元**、高峰 0.006 美元；输入（缓存未命中）非高峰 **0.15 美元**、高峰 0.30 美元；输出非高峰 **0.60 美元**、高峰 1.20 美元，其中非高峰费率为高峰费率的一半<sup>[1]</sup>。以此单价衡量，驾考问答这类单次请求上下文与回答均较短的场景，单次调用成本处于很低的数量级，课程设计期间的调试与演示用量不会产生明显的费用负担。

关于该成本需要说明三点。其一，上述单价来自官方页面中 `deepseek-flash` 的价格档，而项目配置使用的模型别名是 `deepseek-chat`，官方当期定价页的模型列表中已不再单独列出该别名，因此**本文不对"本项目实际按哪一档计费"作出断言**，上述数字仅用于说明成本量级。其二，官方页面明确说明产品价格可能调整，**实际费用取决于调用量、所选模型与调用时的实际定价**。其三，本项目**未对实际调用量进行完整的计量与统计**，因此本报告不给出整个课程设计周期的总费用数字，也不作估算。

**人力成本**方面，本课题为个人课程设计，由本人独立完成需求分析、数据库设计、后端与前端编码、测试与文档撰写，开发过程中借助人工智能编程助手提高编码效率。人力投入属于课程学习的一部分，不产生额外支出。

综合来看，本系统在开发、部署与运行环节均不产生硬件与软件许可费用，外部服务费用规模小且可控，经济上是可行的。

## 2.3 社会效益

从学员角度看，本系统在传统"题库 + 模拟考"的基础上增加了两项能力。一是错题的自动归集与重练：学员答错的题目会被自动记录并区分"高频错、待攻克、已攻克"，复习时可以优先处理反复出错的题目，减少在已掌握内容上的重复投入。二是针对性的答疑：学员可以就某个知识点或某道错题提问，由系统结合所选科目给出解释，相比在论坛检索或等待教练答复，反馈更及时。学情分析部分通过知识点掌握度与薄弱点判定，把"感觉哪一块不行"变成具体的指标，有助于安排复习顺序。

从教练角度看，系统中设计了学员学习数据的查看入口与考试建议确认流程，用于辅助教练掌握名下学员的复习进展；但如前所述，该部分功能本期尚未实现，其效益目前仅为设计层面的预期，本报告不作实际效果方面的推断。

需要客观说明的是，本系统是教学辅助工具，不能替代教练的实际教学与驾驶技能训练，也不对考试通过率作出任何承诺。其能够改善的是理论学习阶段的反馈速度与复习针对性，而学习效果仍取决于学员的投入程度。

从教学层面看，本课题作为课程设计，其过程本身具有实践价值：完整经历需求分析、数据库设计、接口约定、分层编码、接口测试与文档沉淀，并处理了外部服务集成、事务边界、越权控制等在真实工程中常见的具体问题。

## 2.4 安全可行性

本系统在实现中采取了以下安全措施，均可对应到具体代码。

**身份认证**采用 JWT 无状态认证。用户登录成功后由服务端签发令牌，其中携带用户标识、用户名与角色；客户端在后续请求的请求头中携带该令牌；服务端通过拦截器统一解析与校验，校验失败返回未认证状态。令牌设置了有效期（当前配置为 24 小时），过期后需要重新登录。

**权限控制**采用"路径前缀 → 角色"的规则。系统按 `/api/student/**`、`/api/coach/**`、`/api/admin/**` 分别限定学员、教练与管理员访问，由拦截器在进入控制器之前完成角色判定，角色不匹配则拒绝。控制器本身不再重复做权限判断，避免了校验逻辑分散。

**密码处理**方面，用户密码以 BCrypt 哈希值存储，数据库不保存明文，哈希过程加盐，不可逆推。

**越权访问防护**方面，所有涉及个人数据的查询与修改操作均在 SQL 条件中带上当前登录用户的标识，而非仅依据前端传入的记录编号；同时，对于"记录不存在"与"记录不属于当前用户"两种情形，系统返回相同的错误码，避免攻击者通过错误码差异探测记录是否存在。

**日志策略**方面，调用大语言模型的过程只记录必要的业务信息，不记录请求头，以避免将 API 密钥等凭据写入日志。

同时应当指出本系统在安全方面的局限：系统当前运行于本地开发环境，未启用 HTTPS，传输层加密依赖部署环境；大模型 API 密钥以配置项形式由环境变量或配置文件提供，属于常见做法但并非密钥管理的最佳实践；系统未实现验证码、登录失败锁定与接口限流等防暴力破解措施；在并发场景下，练车预约的时段冲突检测采用"先查询后插入"的方式，未建立唯一约束，理论上存在并发写入绕过的可能，这是本项目明确记录在案的取舍。以上局限与课程设计的使用场景（单机演示、不对外提供服务）相适应，但若系统需要对外提供服务，则需逐项补齐。

## 2.5 法律可行性

本系统的运行涉及生成式人工智能服务的提供与个人信息处理两个法律维度，现依据可查证的法规条文作谨慎分析。

**关于生成式人工智能服务。**《生成式人工智能服务管理暂行办法》由国家互联网信息办公室会同国家发展改革委、教育部、科技部、工业和信息化部、公安部、国家广播电视总局联合公布（令第 15 号），2023 年 7 月 13 日发布，自 2023 年 8 月 15 日起施行<sup>[2]</sup>。该办法第二条规定，利用生成式人工智能技术向中华人民共和国境内公众提供生成文本、图片、音频、视频等内容的服务适用本办法；同时明确，未向境内公众提供服务的研发、应用不适用该办法。本办法为课程设计场景下的合规判断提供了直接依据。本系统当前仅在校内、本地环境中用于教学演示，不向公众提供服务，属于上述"未向境内公众提供服务"的情形。但考虑到系统已经具备对外服务的形态，若后续扩大使用范围，则应当按该办法履行相应义务，其中与本系统关系较密切的条款包括：第四条规定提供和使用生成式人工智能服务应当坚持社会主义核心价值观、尊重知识产权与商业道德、尊重他人合法权益并提高生成内容的准确性与可靠性；第七条规定训练数据处理活动中涉及知识产权的，不得侵害他人依法享有的知识产权；第十一条规定服务提供者应当依法履行个人信息保护义务，不得收集非必要个人信息、不得非法向他人提供使用者输入信息和使用记录；第十二条规定对图片、视频等生成内容应当按《互联网信息服务深度合成管理规定》进行标识。

**关于个人信息保护。**《中华人民共和国个人信息保护法》于 2021 年 8 月 20 日通过，自 2021 年 11 月 1 日起施行<sup>[3]</sup>。本系统处理的个人信息包括用户登录名、真实姓名、手机号以及答题记录与预约记录。其中登录名、姓名与手机号属于个人信息，系统未收集身份证件号码、生物识别信息等敏感个人信息。该法第十三条规定了处理个人信息的合法性基础，其中最常用的是取得个人同意；本系统的个人信息来源于账号注册与用户自行填写，属于基于同意的处理。该法第二十四条对利用个人信息进行自动化决策提出要求，明确应保证决策的透明度和结果公平、公正，并对通过自动化决策方式作出对个人权益有重大影响的决定，赋予个人要求说明与拒绝的权利。本系统中学情分析所输出的知识点掌握度与薄弱点判定，属于依据学习行为生成的辅助性分析结果，用于提示复习方向，不对学员的权利义务产生实质影响；但按照该条体现的透明性要求，系统在实现上应当向用户说明该指标的计算口径，本项目已在设计文档中记录了掌握度公式与短板判定规则，具备可解释性。

**关于题库内容来源。** 本系统使用的题目为自行编写的示例题目，数量有限，未复制任何商业题库产品的内容。需要提请注意：若后续引入车管所官方题库或第三方题库产品，应当先确认其使用授权与版权归属，不得直接复制。本报告不就此作出结论，仅作提示。

**需要说明的限制。** 上述分析仅依据公开可查的法规条文，就本系统的功能与数据范围作出说明，**不构成对本系统合规性的保证，也不构成法律意见**。系统若用于实际教学或对外提供服务，应当结合数据来源、服务对象与部署方式另行履行必要的手续与评估。

## 2.6 课程设计规模与实施条件说明

本课题为个人课程设计，由一人独立完成，计划周期约四至五周（含一周缓冲）。系统规模为：数据库 16 张业务表，后端 8 个控制器、38 个 REST 接口，前端覆盖登录、学员端的科目首页、刷题、错题本、学情分析与智能问答页面。所依赖的环境条件为：一台可运行 Java 与 Node 环境的个人计算机、本地 MySQL 数据库、可访问大语言模型开放接口的网络环境，以及上述开源软件工具链。开发方式上，采用"先设计后编码"的顺序推进，即先确定数据库结构与接口约定，再按模块逐个实现并进行接口联调，以降低返工成本。

与课程设计的要求相比，本课题在技术广度（前后端分离、数据库设计、外部服务集成、接口测试）与实现深度（判分算法、学情计算、事务与越权控制）上均达到相应要求；在时间与人力有限的条件下，通过明确的功能取舍保证了已完成部分的质量与完整性。综合技术、经济、社会效益、安全与法律五个方面的分析，本系统的设计与实现是可行的。
