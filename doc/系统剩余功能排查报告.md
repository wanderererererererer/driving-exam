## 一、结论摘要

当前系统不是“只有静态页面”的原型。登录认证、学员刷题/错题/学情/模考/预约/聊天、教练学员管理/预约/聊天、管理员主要 CRUD、AI 与 RAG 代码均已存在，前后端接口路径总体一致。

但仍有几类高优先级缺口：

1. **AI/RAG 在新部署中可能直接不可用**：AI 问答在调用 DeepSeek 前强制走 Embedding + Qdrant 检索，检索异常不降级；Compose 默认不启动 Qdrant，且代码中没有知识入库的运行时入口。
2. **模拟考试存在数据一致性风险**：试卷/题目被管理员禁用或删除会影响进行中的考试；试卷可包含重复题目；暂存答案不校验题目属于本卷；试卷时长/及格分缺少下界校验。
3. **认证状态不会随账号禁用或角色修改即时失效**：JWT 只在签发时检查账号状态，之后完全信任 token 中的角色；没有 logout/黑名单机制。
4. **预约存在并发重复预约风险**：冲突检查是“先查询再插入”，数据库没有时段唯一约束，代码也不加锁。
5. **前端模考只显示总分，不展示逐题报告；超时不会自动交卷；AI 对话刷新后当前消息不恢复**，影响演示完整度。
6. **管理员 Excel 导入、管理员接口、AI 问答、Day28 教练新增接口、Day29 Dashboard 均缺少当前可复核的运行测试证据**。
7. **Docker 前端镜像仍是构建时烘焙的静态文件**：本地 `dist` 更新不会自动进入容器，需要重建 frontend 镜像。
8. **文档与当前实现存在明显漂移**：多份报告/答辩素材仍称 RAG、聊天、教练、管理员未实现；API 设计文档还列有实际不存在的接口。

综合判断：系统核心骨架完整，但距离“可稳定演示、可重复部署、可答辩说明”还有一轮以数据一致性、AI 可运行性和验收证据为主的收尾工作。

## 四、前后端、权限、数据库对应关系

### 4.1 权限边界

- 后端路径规则由 `driving-exam-server/src/main/java/com/driving/exam/server/config/PathRoleRule.java` 定义：
  - `/api/auth/**`、`/api/common/**`：任意已认证用户；
  - `/api/student/**`：`STUDENT`；
  - `/api/coach/**`：`COACH`；
  - `/api/admin/**`：`ADMIN`。
- JWT 拦截器 `JwtInterceptor.java` 负责：
  - 从 `Authorization: Bearer` 读取 token；
  - 校验签名与过期；
  - 读取 token 中的 `userId`、`username`、`role`；
  - 按路径校验角色；
  - 将身份写入 request attribute。
- 前端 `frontend/src/router/index.ts` 的前置守卫只做页面导航体验，角色来自 `localStorage`；真正的数据权限仍由后端负责。
- 预约、聊天、教练学员详情等业务服务在 SQL 中再次使用 `student_id` / `coach_id` / `coach_student.id` 做归属收敛，未直接把前端传入的学生 ID 当作授权依据。

**已确认的权限风险**：JWT 拦截器不重新查询 `sys_user`，所以账号被管理员禁用或角色被修改后，已签发的 24 小时 token 仍然可以使用；同样，禁用用户如果已有绑定，聊天服务只校验角色和绑定，不校验账号状态。

#### P1-1 AI 问答在默认部署下可能完全不可用

- `AiChatServiceImpl.java:102-105`：在调用 DeepSeek 前强制调用 `knowledgeRetriever.retrieve(...)`，没有 try/catch，也没有“检索失败后无上下文继续回答”的降级。

#### P1-2 模拟考试内容与结算数据可能不一致

**状态：存在疑似问题，部分操作未防护。**

证据：

- `ExamServiceImpl.java:170-177` 的 `answer()` 只校验考试归属和状态，不校验 `questionId` 是否属于当前试卷。
- `ExamServiceImpl.java:322-328` 的 `loadPaper()` 要求试卷 `status=1`；`submit()`、`report()`、`resume()` 都调用它。管理员禁用试卷后，已经开始的考试可能无法交卷、恢复或查看报告。
- `AdminService.deleteQuestion` 只检查答题记录，不检查 `exam_paper_question`；题目被删除后，`ExamServiceImpl.loadPaperItems` 会静默跳过缺失题目，但试卷/考试保存的总分不随之调整。
- `AdminService.validatePaper` 未检查重复 `questionId`；同一道题可以在试卷中重复计分。
- `AdminService.applyPaper` 未校验 `duration`、`passScore` 下界；`duration=0` 会导致立即超时，负及格分会使考试异常通过。
- `ExamServiceImpl.start()` 的“查找进行中考试再插入”没有事务、锁或唯一约束保护；并发开始可能生成多条进行中的考试记录。
- `ExamServiceImpl.answer()` 的注释放行“多余答案在结算时忽略”，但这会让数据库中留下不属于试卷的答案记录。

影响：

- 管理员在演示前调整题目/试卷，可能导致学员已有考试无法交卷或成绩总分不一致。
- 并发开始或重复题目会造成成绩、统计和报告错误。
- 这些不是前端显示问题，而是数据一致性问题，优先级应高于 UI 修饰。

建议：

1. 试卷题目做去重，保存时校验 `duration >= 1`、`passScore >= 0` 且不超过总分。
2. 交卷/报告不要因试卷被禁用而失败；至少允许已开始的考试按创建时快照结算，或禁止禁用有关联考试的试卷。
3. 删除/禁用题目时检查关联试卷；对已有考试的试卷建立不可变快照或明确版本策略。
4. `answer()` 校验题目属于当前试卷；`start()` 增加锁/唯一约束或数据库级别的进行中约束。

#### P1-3 账号禁用/角色变更不会使已签发 JWT 失效

**状态：存在权限风险，已实现但缺少撤销机制。**

证据：

- `JwtInterceptor.java:55-79` 只从 token 读取 `role`，不查询 `sys_user`；没有状态或 role 复查。

#### P4-3 Docker 初始化只在空卷执行，缺少迁移机制

**状态：部署风险。**

证据：

- `docker-compose.yml` 仅把 SQL 挂载到 `/docker-entrypoint-initdb.d`；MySQL 官方镜像只在空数据卷初始化时执行。
- 仓库没有 Flyway/Liquibase 或其他迁移工具。
- `sql/schema-mock-exam-answer.sql` 是独立脚本，但 Compose 没单独挂载，依赖 dump 已包含该表。
- 初始化脚本包含 `DROP/DELETE` 类内容，只能用于独立空卷。

影响：

- 已有 `mysql-data` 卷不会自动获得新表/字段/种子数据；更新版本时需要手工迁移。
- 如果 dump 与增量脚本不同步，重装和旧卷会出现不同结构。

建议：

- 明确“仅空卷初始化”的部署边界；
- 后续引入迁移脚本/版本表，或至少维护一份可重复执行的增量 SQL；
- 不在共享/验收数据库直接执行初始化脚本。

#### P4-4 后端健康检查不能证明数据库可用

**状态：部署配置问题。**

证据：

- `docker-compose.yml` 的 backend healthcheck 接受 `/api/auth/me` 返回 401 或 200。
- `JwtInterceptor` 对未带 token 的请求直接返回 401，不访问数据库。
- 因此容器健康可能只说明 HTTP 服务启动，不说明 datasource/schema 正常。

影响：

- `depends_on: backend healthy` 可能在前端启动时后端数据库尚不可用，导致首次页面接口失败。

建议：

- 增加一个明确的健康/就绪端点（可匿名、只查数据库简单查询），或在 healthcheck 中区分启动与就绪；
- 不在生产暴露敏感信息。

#### P4-5 本地配置和凭据分散

**状态：安全/维护风险。**

证据：

- `driving-exam-server/src/main/resources/application.yml` 包含本地默认数据库凭据和 JWT 默认值；

影响：

- 容易误提交或在演示机泄露；JWT 默认值若被用于真实部署会削弱安全性。

建议：

- 保持 `.env`/本地配置不入库；
- 将 JWT/DB 密码改为必填、无默认值；
- 清理不再使用的配置副本，并确认 `.gitignore` 覆盖完整。
